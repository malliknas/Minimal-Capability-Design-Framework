Designing Lightweight AI Agents for Edge Deployment

A Minimal Capability Framework with Insights from Literature Synthesis

Appendix B: Configuration

Documents the configuration environment and experimental setup, including hardware specifications, model pools, memory and token budget parameters, validation frameworks, and reproducibility protocols crucial for the reliability of the study.
This configuration framework ensures reproducible, statistically valid results while maintaining the ecological validity of real-world deployment constraints. All parameters were optimized for browser-based execution environments typical of edge AI deployment scenarios.

B.1 Test Environment Specifications

B.1.1 Hardware Configuration

The MCD framework validation was conducted using the following standardized hardware configuration:
Primary Testing Platform:
Platform: Windows 11 (NT 10.0, Win64 x64)
Memory: 8GB RAM
CPU Cores: 8 cores
GPU Support: WebGPU Available
Browser: Chrome 140.0.0.0 (also tested on Edge 140.0.0.0)
Runtime Environment: WebAssembly (WASM) with local browser execution

Browser Engine Details:
User Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/140.0.0.0 Safari/537.36 Edg/140.0.0.0
JavaScript Engine: V8
WebGPU: Supported and Available
WebAssembly: Full WASM support enabled

B.1.2 Model Configuration and Quantization Tiers

Available Model Pool (135+ models tested):
The testing framework included access to 135+ quantized models across different parameter scales and optimization levels.

Primary Test Models by Quantization Tier:
Q1 Tier (Ultra-Minimal - ~300MB)
Primary: Qwen2-0.5B-Instruct-q4f161-MLC
Backup: SmolLM2-360M-Instruct-q4f161-MLC
Memory Target: <300MB
Use Case: Ultra-constrained environments, proof-of-concept validation

Q4 Tier (Balanced - ~600MB)
Primary: TinyLlama-1.1B-Chat-v1.0-q4f161-MLC
Secondary: Qwen2.5-0.5B-Instruct-q4f161-MLC
Memory Target: 500-700MB
Use Case: Production deployment, optimal efficiency-quality balance

Q8 Tier (Performance - ~800MB+)
Primary: Llama-3.2-1B-Instruct-q4f321-MLC
Secondary: Llama-3.1-8B-Instruct-q4f161-MLC-1k
Memory Target: 600-1200MB

Extended Model Pool (Validation Coverage):

B.2 Execution Parameters

B.2.1 Token Budget Configuration

Tier-Specific Token Limits:

Tier Max Tokens Temperature Top-P Frequency Penalty Presence Penalty
Q1 60 0.0 0.85 0.3 0.1
Q4 90-120 0.1 0.8 0.5 0.3

Prompt Engineering Parameters:
System Prompt: Null (stateless by design)
Dynamic Prompting: Enabled for all tiers
Template Protection: Added to prevent contamination
Context Window: Optimized per model (1k-4k tokens)

B.2.2 Memory Management Configuration

Memory Monitoring:
Pre-execution Memory: Baseline measurement before each test
Post-execution Memory: Memory usage after completion
Memory Delta: Tracked for resource efficiency scoring
Stability Threshold: ±50MB considered stable
Memory Budget: 512MB target, 1GB maximum

Resource Limits:
Latency Budget: 500ms average, 2000ms maximum per query
CPU Usage: Monitored but not limited
Browser Stability: Crash detection and recovery enabled
Batch Processing: Disabled to ensure isolation

B.3 Test Suite Configuration

B.3.1 Cross-Validation Settings

Statistical Configuration:
Repeated Trials Design: n=5 independent measurements per variant
Statistical Analysis: Categorical performance differences with Fisher's Exact Test for binary outcomes; descriptive statistics for continuous metrics
Confidence Intervals: 95% CI (Wilson score method) calculated for completion rates
Sample Acknowledgment: Limited statistical power (n=5 per variant); validation relies on extreme effect sizes and cross-tier replication (Q1/Q4/Q8)
Random Seed: Fixed for reproducibility across test iterations

Measurement Tools:
Primary: performance.now() API for high-resolution timing measurements
Secondary: Browser DevTools integration for resource monitoring
Validation: Cross-platform compatibility testing (Chrome, Firefox, Edge)
Error Handling: Comprehensive failure classification and logging

B.3.2 Domain-Specific Parameters

W1: Medical Appointment Domain
Slot Requirements: Doctor, Date, Time, Patient Name, Reason
Validation Rules: Date format, time slot availability, doctor specialization
Success Criteria: ≥4/5 slots correctly extracted
Fallback Depth: Maximum 3 clarification loops

W2: Spatial Navigation Domain
Safety Classification: Critical path validation required
Hazard Types: Wet floors, construction zones, restricted areas
Route Validation: Point-to-point pathfinding accuracy
Memory Constraints: Stateless route recalculation required

W3: Failure Diagnostics Domain
Error Categories: Server, Database, User Access, Performance, Communication
Response Structure: Component identification + structured troubleshooting
Technical Depth: Appropriate for Q1 (basic) to Q8 (detailed) tiers
Template Protection: Anti-contamination filters for formal language patterns

B.4 Validation Framework Configuration

B.4.1 MCD Compliance Scoring

Alignment Metrics:
Minimality Score: Token efficiency relative to semantic value
Boundedness Score: Adherence to reasoning depth limits (≤3 steps)
Degeneracy Score: Component utilization rates (≥10% threshold)
Stateless Score: Context reconstruction success without persistent memory

Classification Thresholds:
MCD-Compliant: Score ≥0.7
MCD-Compatible: Score 0.4-0.69
Non-MCD: Score <0.4
Over-Engineered: Redundancy Index >10

B.4.2 Performance Classification

Tier Performance Categories:
Excellent: ≥90% completion rate, optimal resource usage
Good: 75-89% completion rate, acceptable efficiency
Acceptable: 60-74% completion rate, within memory bounds
Poor: <60% completion rate or excessive resource consumption

Edge Deployment Classification:
Edge-Superior: <400ms latency, <300MB memory, 100% success
Edge-Optimized: <500ms latency, <500MB memory, ≥90% success
Edge-Compatible: <750ms latency, <700MB memory, ≥75% success
Edge-Risky: <1000ms latency, <1GB memory, ≥60% success
Deployment-Hostile: Exceeds edge deployment constraints

B.5.2 Result Classification Schema

Success Determination:
Technical Success: Task completion within resource constraints
Semantic Success: Meaningful and contextually appropriate responses
MCD Alignment: Adherence to framework principles
Edge Viability: Deployment compatibility in constrained environments

Failure Categories:
Technical Failure: Crashes, timeouts, resource exhaustion
Semantic Failure: Hallucination, irrelevant responses, safety violations
Framework Violation: Non-compliance with MCD principles
Template Contamination: Use of placeholder text or formal letter patterns

B.6 Reproducibility Parameters

B.6.1 Environment Standardization

Browser Configuration:
Cache Management: Cleared before each test session
Extension Isolation: Clean browser profiles used
Network Conditions: Local execution only, no external API calls
Resource Monitoring: Real-time memory and CPU tracking

Model Loading Protocol:
Pre-load Phase: All three tiers loaded before testing begins
Warm-up Period: Initial inference to stabilize performance
Baseline Measurement: Resource usage recorded before first test
Isolation Protocol: Memory reset between test variants

B.6.2 Statistical Validity Assurance

Randomization Controls:
Test Order: Randomized variant presentation
Model Selection: Systematic tier progression (Q1→Q4→Q8)
Cross-Validation: Stratified sampling across approach types
Temporal Controls: Time-of-day effects minimized through session distribution

Quality Assurance:
Inter-Rater Reliability: Automated scoring validation
Test-Retest Stability: Repeated measures for key findings
External Validation: Cross-platform compatibility verification
Data Auditing: Complete experimental trace logging
